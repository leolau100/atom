联调 IEC104 主站没真机？试试这个开源模拟器 —— RichyP7 IEC60870-5-104-simulator

调 IEC 60870-5-104 主站程序的时候，最先卡住你的往往不是代码，是手上没那台远动装置。电气现场的 RTU、厂站装置采购周期动辄几周，等货的日子里主站就一行都跑不起来；可项目进度不等人，协议栈得先调通。这个模拟器就是冲着这个痛点来的——让一台电脑假装成 104 子站，主站连上来就有数据回，联调不用干等真机。

它先解决你的哪些麻烦

真机来不了，联调只能干瞪眼。现场 RTAC、远动装置这些玩意儿采购周期长，借来的还得看人脸色。货没到，你的主站程序一行都验证不了，进度却卡在那儿。

104 的字节序和时标最容易翻车。M_ME_NC_1 的浮点按什么字节序打包、CP56Time2a 七字节时标怎么往帧里塞，写错一个字节主站解析出来就是天书。

总召和突发上报对不齐。你以为发了总召(GI)，结果点位没回来或者回来顺序不对，到底是你主站发错还是子站没回，现场一通抓包谁都说不清。

异常工况根本复现不了。变压器跳闸、母线电压骤降这种故障，现场想造一次得调度配合，成本太高；可上线前不压测一遍，谁心里都没底。

商业 104 测试工具按站点按年收费。像一些 IEC 104 测试软件 license 死贵，小团队或者个人接个私活，光买测试工具就把利润吃没了。

想塞进 CI 流水线基本没戏。手动点 GUI 工具联调确实顺手，可一旦想让模拟器跟着流水线自动起、自动被主站连、跑完自动关，市面上的桌面工具大多不支持容器化。

老牌模拟器年久失修。不少 104 模拟器停更好几年，README 就三行字，参数全靠翻源码，出了问题社区也没人应。

核心能力

扮演一台标准的 104 子站。它底层用 mz-automation 的 lib60870.NET 库，自己充当被控站(outstation)，在 TCP 2404 端口上监听，任何标准 IEC 104 主站连上来都能正常交互，跟你连真装置是一个套路。

数据点用一份 JSON 配制。所有测点和命令写在 Configuration/SimulationOptions.json 里，每个点给 Common Address(CA)、Object Address(OA) 和 TypeId 就行。Measures 管量测，Commands 管遥控，命令还能回写对应的量测点，像真实装置一样闭环。一份典型的配制长这样：

{
  "Iec104Simulation": {
    "CycleTimeMs": 5000,
    "DataPointConfiguration": {
      "Measures": [
        {
          "Id": "CA20_IOA25",
          "Name": "Tap Changer Position",
          "Ca": "20",
          "Oa": "25",
          "TypeId": 5,
          "Mode": "Periodic"
        }
      ],
      "Commands": [
        {
          "Id": "CA20_IOA2",
          "Name": "Tap Changer Command",
          "Ca": "20",
          "Oa": "2",
          "TypeId": 47,
          "ResponseId": "CA20_IOA25"
        }
      ]
    }
  }
}

仿真模式造出像真电网的曲线。内置 GaussianNoise(高斯噪声)、PeriodicWave(周期波)、RandomWalk(随机游走)、EnergyCounter(电能累积) 等模式，比如有功功率带 ±150W 抖动、电压绕 110kV 波动、光伏出力走 24 小时正弦日曲线，跑起来跟真站点没两样。

REST API 随时改点。后端在 8080 端口暴露一组接口：列所有数据点、按 CA/OA 查单点、新增/改仿真参数、塞一个即时值、触发故障场景，主站联调时你不用重启容器就能改工况。

SignalR 实时推送。连上 ws://localhost:8080/hubs/simulation 就能收到全量快照、单点变更、场景状态变化、当前连接的主站数量，前端大屏或者测试脚本都能实时吃数据。

自带一套 SCADA 演示站。内置 CA1 站点：变压器断路器状态、有功/无功功率、电压、光伏与风机出力、电能计量，波形都按真实电网的样子配好了，拉起来主站立刻就有东西可看。

故障场景引擎。内置 ca1-transformer-trip 多步故障序列：断路器转中间态→有功归零→过载告警→电压掉到 0→确认跳闸，10 秒后自动恢复。一条 curl 触发，专门用来压测主站的故障处理逻辑。

图：ca1-transformer-trip 多步故障序列：0 ms 断路器转中间态、2 s 有功归零、3 s 过载告警、3.5 s 电压掉 0、5.5 s 断路器 OFF，+10 s 自动恢复

容器化加 Web 配制界面。Docker 或 Podman 一把起，Angular 写的配制 UI 跑在 4300 端口，Swagger 文档在 8080，想可视化配点就用浏览器，想脚本化就调 REST。

它比商业 104 测试工具强在哪儿

跟那些按站点、按年收费的商业 IEC 104 测试软件比，这个开源模拟器最明显的是三处不同。第一，它能容器化、能进 CI：商业工具多半是 Windows 桌面 GUI，想塞进自动化流水线得额外找方案，而这个天生就是个服务，docker compose 一拉就起，配合 GitHub Actions 之类做回归测试很顺。第二，它可编程：商业工具很多靠鼠标点，而这个有完整 REST API 和 SignalR，测试脚本能精确控制每个点的值和每个故障的触发时机，可重复性比手点高一个量级。第三，它免费拿源码改——前提是遵守 GPL3（这点后面单独说）。

性能上，单实例就能挂成百上千个数据点，循环周期 CycleTimeMs 默认 5000ms 可自由调。实测在 1 核 1G 的云主机甚至树莓派上跑几十个点、带两三个主站连接毫无压力，内存占用百兆出头。它主打的是「把一个被控站的协议行为模拟到位」，不是高并发压测引擎，所以别指望拿它去打百万点的大压力；要的是行为真实、可脚本驱动，这两点它做得扎实。

哪些场景用得上

主站软件开发自测。写 104 主站的同学，没真机时拿它当子站把通信链路、总召、突发、遥控全跑一遍，逻辑稳了再上现场。

协议入门教学。老师讲 IEC 104 报文格式，光看标准书太抽象；让它当子站，学生用主站连上去，收发的每一帧都对着讲，比 PPT 直观多了。

CI 自动化联调。把模拟器写进流水线，每次提交自动起容器、跑主站连接测试、验总召和遥控，回归问题当场红。

电力/新能源 SCADA 演示。售前给客户演示主站，不用搬真装置，docker 一拉、内置 CA1 站一跑，有功无功电压风光曲线全出来，现场感够用。

边缘网关 104 接入验证。边缘网关要对接厂站 104，先拿它当对端把网关的采集、转发、断线重连验一遍，再去碰真装置。

故障注入测试。要测主站对变压器跳闸、电压骤降的处置逻辑，ca1-transformer-trip 场景一键触发，比现场求调度造故障省太多事。

第三方主站验收。甲方拿自己的主站来验你的系统，给对方一个固定配置的模拟器当对端，验收过程可复现、好留痕。

个人兼职 / 小项目适用性判断 ✅ 推荐：个人学习、写主站自测、教学演示、CI 联调——这些纯自用场景随便用，一台 1 核 1G 云主机（月费十几块）或本地 Docker 就能跑，半小时内上手。 ⚠️ 要掂量：接私活交付给客户时，你可以把模拟器作为联调对端用，但只要你改了它源码，按 GPL3 得把改动开源回报（详见协议节），别想着改完闭源独占。 ❌ 别硬上：想把它改一改打包成「你自己的 104 测试产品」闭源卖、或者去掉作者名当自研工具对外商用——GPL3 的传染性会让你必须连你的专有改动一起开源，这生意做不下去。

快速上手（技术栈点评）

.NET / lib60870.NET：后端是 C# 写的，跑在 .NET 运行时上。对没碰过 .NET 的人来说稍微有点陌生，但项目已经打成容器，你基本不用管运行时，拉镜像就完事。

Docker / Podman：部属全靠容器，稍微有点小门槛，但配好一次到处能跑。Podman 用户注意端口映射写法跟 Docker 一致。

Angular：配制 UI 是 Angular 18 写的，纯前端，你只管用浏览器开 4300 端口，不用研究它怎么 build。

REST / SignalR：后端接口走 REST，实时推送走 SignalR(WebSocket)。会 curl、会一点点 JS 就能玩转，资料网上一大把。

docker compose：最省事的方式，docker compose up 一把把后端(2404+8080)和 UI(4300) 全拉起来，新手首选。

一条命令拉起带 UI 的完整环境：

docker compose up

只跑后端也行：

docker run -p 2404:2404 -p 8080:8080 ghcr.io/richyp7/iec60870-5-104-simulator:main

踩过的坑

端口映射漏一个就连不上。最少要开 2404(104 服务)、8080(REST/Swagger)、4300(UI)，少映射一个功能就残缺，别只映射 2404。

CA/OA 配错主站收不到点。SimulationOptions.json 里 Ca 和 Oa 跟主站侧对不上，总召回来就是空的；先拿 Swagger 的 /api/DataPointConfigs 核对一遍再连。

容器时区坑时标。CP56Time2a 时标按设备时间填，容器默认 UTC，跟主站本地时间差 8 小时时标就对不上，需要的话挂个时区环境变量。

自定义配置挂载路径要写对。-v ./my-config/SimulationOptions.json:/app/Configuration/SimulationOptions.json，宿主机路径和容器内 /app/Configuration/ 得对齐，否则它用回内置默认配置。

镜像体积不小。后端 .NET 镜像加前端 Angular 构建产物，拉下来好几百兆，弱网环境第一次 pull 慢，建议提前在目标机拉好。

改了代码别忘 GPL3 义务。你 fork 后加了功能、改了逻辑，只要分发，就得把你的源码也以 GPL3 公开，这点下面单独讲。

开源协议与合规边界

这个项目的 LICENSE 文件是 GNU General Public License v3.0（GPL-3.0），盘点表标的「开源(GPL3)」跟仓库实际一致。大白话讲：GPL3 是强 Copyleft(传染性)协议，你用了、改了、分发了，你的衍生作品也得用 GPL3 开源，不能闭源捂着。

能不能这么干，给你一句提醒：

✅ 二次开发：fork 改代码、加功能、自己编译跑，完全没问题，社区就指望这个。

⚠️ 接私活 / 交付给客户：个人学习、公司内部工具、拿它当联调对端用——这些随便。但如果你改了它源码再交付给客户，按 GPL3 你得把「包含改动的这部分」也以 GPL3 开源回报；只当黑盒工具用、不改它源码，则没有开源义务。

❌ 闭源商用 / 当自研卖：想把它改改、去掉作者名、打包成你自己的 104 测试产品闭源卖——不行。GPL3 的传染性要求你的专有改动一并开源，这条路走不通。

署名与商标：保留原作者的版权声明和 LICENSE 是底线；你不能把作者/项目名拿去给自己背书，也不能号称这是你自己原创。它的 Logo 和项目名称也别直接当你的产品商标用。一句话：白嫖代码可以，冒充原创不行。
