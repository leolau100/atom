大家好，我是aric。

用编码智能体的工程师，多少都遇到过这种情况：需求说了三遍，智能体交上来的东西还是对不上；让它改个 bug，它顺手把旁边两个模块也重构了。代码量涨得飞快，敢合进主干的没几行。

mattpocock/skills 是 Matt Pocock 的个人仓库。他是 Total TypeScript 的创始人，用他自己的话说，这个仓库是"我每天用来做真正工程的智能体技能，不是 vibe coding"。仓库 2026 年 2 月 3 日上线，截至 10 月 19 日，GitHub Star 约 29.6 万，Fork 约 2.5 万，未关闭的 issue 近 200 个，MIT 许可。

本文讲清楚三件事：这些 skill 到底是什么、怎么装进你的智能体、用之前需要知道哪些限制。

它解决什么问题？

先看 skill 是什么。一个 skill 就是一份 Markdown 文件，里面写清了某个工作规程：什么时候触发、分几步走、每步问什么、产出什么。编码智能体读到它，就按这套规程执行，而不是每次凭即兴发挥。GitHub 把这个仓库的主语言标为 Shell，但主体内容其实是几十个 SKILL.md 文件。

这个仓库要修的是智能体开发里四个反复出现的失败模式，README 把它们列得很直白：

智能体没领会你的意图，做出来的东西驴唇不对马嘴；

智能体话太多，项目里的黑话它不会用，一个概念能扯出二十个词；

代码跑不起来，智能体没有反馈回路，只能瞎猜；

功能是有了，代码结构烂成一团，改不动也不敢改。

针对这四类问题，仓库把对应的规程写成了可以直接调用的 skill。进入官方 README 正式清单的一共 27 个，分在工程和生产力两个目录下。

核心能力

先问清楚再动手：grilling 系列

仓库里安装量最高的是 grill-me，在 skills.sh 目录站上累计安装超过 140 万次。它做的事情就一件事：拉着你反复追问，直到设计树上的每个分支都有答案，才允许进入实现。

工程目录里的 grill-with-docs 是同一机制的加强版：追问的同时把项目的领域模型建起来，术语写进 GLOSSARY.md，重要决策记成 ADR。作者认为这是整个仓库里最值得试的技巧——智能体有了共享语言，变量和文件的命名会自然统一，代码库对智能体更好导航，消耗的 token 也会降下来。

把反馈循环还给智能体：/tdd 与 /diagnosing-bugs

tdd 这个 skill 把红-绿-重构循环固化成流程：先写失败测试，再实现，一次只做一片垂直切片。diagnosing-bugs 针对难 bug 和性能回退，流程是先造一个能对这个 bug 变红的反馈环境，再最小化复现、提出假设、加埋点、修复、补回归测试。

这类 skill 的价值在于把工程师熟知的纪律翻译成智能体能执行的步骤，不用每次在对话里重新教一遍。

盯着代码结构：to-spec 与 improve-codebase-architecture

to-spec 把当前对话直接整理成规格文档，发布到 issue tracker，不做额外访谈。improve-codebase-architecture 则扫描代码库，找出可以"加深模块"的位置，生成一份可视化 HTML 报告供你挑选。

作者自己的建议是每隔几天跑一次架构扫描，并且提醒这是一个 survey 而不是 rescue——老代码库里它能找到真实的候选点，但不会替你理顺烂摊子。

user-invoked 与 model-invoked 两层调用

27 个 skill 按调用方式分两类。user-invoked 只能由你输入斜杠命令触发，职责是编排流程；model-invoked 既可以手动调，也能在任务匹配时被智能体自己捡起来用，承载可复用的规程。前者可以调用后者，两个 user-invoked skill 之间不能互调。理解这个分层，才知道该把哪个 skill 挂到哪一步。

可组合、可改写，不绑定模型

作者在 README 里明确了对标对象：GSD、BMAD、Spec-Kit 这类框架试图接管整个开发流程，控制权被拿走之后，流程里的 bug 反而难定位。这个仓库的定位相反——skill 要小、要好改、要能拼装，作者的原话是"随便改，改成你自己的"。

放到实际场景怎么用？

以 Claude Code 为例，一条命令装插件：

claude plugin install mattpocock-skills@claude-plugins-official

插件方式会自动更新。用其他智能体的话，README 给了对应路径：Codex 用 codex plugin marketplace add mattpocock/skills 加市场再装插件；GitHub Copilot 类似，但要额外在 ~/.copilot/settings.json 里登记这个 marketplace；Gemini CLI 和不走插件机制的智能体（Cursor、opencode、Devin 等）走 npx skills@latest add mattpocock/skills -a ＜agent＞，把可编辑文件拷进项目，更新靠手动重跑。

两种方式每个智能体选一种，README 特别说明同时装会导致每个 skill 出现两份。

装完之后，在每个仓库里跑一次 /setup-matt-pocock-skills，它会问三个问题：用哪个 issue tracker（GitHub、GitLab 或本地文件）、triage 时打什么标签、文档放哪里。配完之后，典型用法是接到需求先跑 /grill-with-docs 对齐意图，再用 /to-spec 落成规格，/implement 按规格施工，收尾前跑 /code-review。

在 skills.sh 目录站上，这个仓库的累计安装量超过 2800 万次，grill-me、grill-with-docs、improve-codebase-architecture、tdd 四个 skill 的单项安装量都过了百万。数字来自第三方站点统计，不是 GitHub 官方指标，但能看出哪些技能被真正用了起来。

有什么限制？

语言门槛。README、skill 正文和 issue 区都是英文，中文团队要用得先过语言关。

初始化成本。不跑 /setup-matt-pocock-skills 的话，triage、wayfinder 这类围绕 issue tracker 运转的 skill 无处发力。

更新机制分裂。插件方式自动更新，npx 方式手动更新；misc 目录下的自留工具不分发进插件，in-progress 目录是公测 beta，README 明说它们可能随时改动或消失，且没有文档页。

单作者项目。贡献者只有 4 人，规程深度绑定 Matt 个人的工作习惯，照搬前最好先读仓库里的 GLOSSARY.md 和 SCOPE.md，看看和他的风格差多少。

效果取决于模型。"任何模型都能用"是作者声明，skill 本质是提示词，执行质量的上限仍由智能体本身决定。

适合什么团队？

已经在日常使用 Claude Code、Codex 或 Copilot，且对输出质量不稳定有体感的工程师，这个仓库几乎可以即装即用。想把 TDD、代码评审、领域建模这些纪律固化下来、减少每次对话重复交代成本的团队，也值得投入一个下午通读一遍。

两类人不建议跟风：平时不碰编码智能体的团队，装了对零收益；寻找一站式开发框架的人，作者自己就说了 GSD、BMAD、Spec-Kit 是另一条路，这个仓库给的是零件，不是整车。

总结

mattpocock/skills 的价值不在技术栈，而在于把资深工程师的日常纪律写成了智能体可执行的规程。不到 9 个月堆到 29.6 万 Star，说明"受够了智能体自由发挥"的工程师远比想象中多。装不装另说，把 README 里那四个失败模式对照一遍，就大概知道自己团队的智能体流程缺在哪。
